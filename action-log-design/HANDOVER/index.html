    How a chunk is built here¶

    Every capture chunk has the same three parts. 5.1d (respite, commit 31f73117) is the shortest worked example; read its diff before writing a new one.

    1. The rules code tells play observers. One call where the thing happens: GameSystem.NotifyPlayObservers("<moment>", ...). Keep it generic: say what happened, not what History should write. Hooks in DMHub Game Rules/ stay system-neutral.
    2. Draw Steel V/HistoryCapture.lua handles the moment. Add a handler and list it in the GameSystem.RegisterPlayObserver("history", {...}) table at the foot of the file. Start it with if not History.Enabled() then return end. Write a line with WriteLine (when it has a creature) or build an entry and call History.AddCombatFacts then History.Write.
    3. Draw Steel V/HistoryTray.lua words it. A branch in LineWords for the new family; the small text under a line is the entry's causetext. Add the family and any new fields to the HistoryEntry annotations in Draw Steel V/History.lua.

    Things that are easy to get wrong:

    • One writer per event. Decide which client writes (the one that rolled, the host, the Director who clicked). Two clients writing the same event doubles it.
    • What players may read is cut in one place: ForPlayers in History.lua, applied when an entry is read. Put a new visibility rule there, never in the tray. The Director check is dmhub.isDM everywhere, the Codex's standard.
    • Wording comes from COPY.md. Anything not signed there is proposed to James first, in the reply, and built only after he agrees. Withdrawn lines are marked in COPY.md.
    • A line that opens a detail card must be listed in HasCard (HistoryTray) and handled in History.Story and the title code in HistoryCard.lua.
    • Does it earn a line? History answers "what just happened and why" during play. James cut the downtime roll lines because the project and the Respite already record them. When another surface already holds the record, write only what changes the table.

    Checking and committing¶

    • Syntax: /d/dependencies/lua/bin/luac.exe -p "<file>"
    • Types (ceiling is zero): from PowerShell in the repo root, & D:\tools\lua-typing\check.ps1 -Files "<file>","<file>". To see the problems, pipe to Select-Object -First 30. A comment block placed between a function and its doc comment causes undefined-doc-param; keep doc comments directly above their function.
    • ASCII only in Lua, comments included.
    • Edits: several of these files are CRLF. Edit with exact-string replacement that keeps line endings (a small Python script using io.open(path, newline='') has worked all day).
    • Commit one chunk at a time: git -c core.autocrlf=false add -- <paths>, check git diff --cached --stat, then git commit -q -m "history: <what>" -- <paths>. Always name the paths: the index is shared. The pre-commit hook re-runs the type check.

    Running it¶

    • Use the dev Codex, D:\dmhubclient\MCDMHub\Codex.exe, test game TwistedRainbowWaywornGuardian. It reads Lua straight from D:\draw-steel-codex.
    • Restart, do not reload. The bridge's reload does not reliably re-read changed files. Stop only the Codex.exe whose path is the dev one (leave any other codex.exe), then Start-Process it with -WorkingDirectory "D:\dmhubclient\MCDMHub" and -ArgumentList "--gameid","TwistedRainbowWaywornGuardian", and poll http://localhost:19876/health until inGame is true and loading is false. About 15 s.
    • Bridge: POST /execute with {"code": "<lua>"}; GET /screenshot; POST /mouse?action=move|click&x=&y=&button=left (send an empty body with -d ""). Use the bridge's virtual mouse, never the OS cursor.
    • Fed tests go on a scratch map. Write test entries with map = "probe-<name>". A fed entry with an encounter on a real map counts as an encounter and can push real rows out; that happened once today. Where a handler writes to game.currentMapId and cannot be redirected, feed only entries with no encounter, and tell James what you left behind.
    • Prefer the real code path over a fed notification. Today's best checks ran the real function on a detached object: creature:Rest on a DeepCopy of a Hero, DTProject:AddRoll on a project attached to no sheet. Neither changed the game.
    • Do not change James's game state without saying so first. Anything that heals, levels, completes a project or shows a banner to every client is his to run.
    • Engine changes: close the dev Codex and Unity, then powershell -NoProfile -ExecutionPolicy Bypass -File "D:\dmhubclient\build.ps1" windows -DevKey in the background (1 to 2 minutes incremental). Success is 0 error CS lines and [BuildScript] Windows build succeeded in D:\dmhubclient\build-windows.log.

    Decisions James made today that are not obvious from the code¶

    • Movement: a creature's own move writes nothing, teleports included. Only movement done to someone is recorded.
    • Dropped from scope: Otherworldly Grace's save-ends change, Game of Chance rolls, character-creation rolls, the Lucky d10, delve and chest rolls, the Encounter of the Week negotiation and town, and downtime roll and adjustment lines.
    • After release: the Acolyte's Patron's Gaze roll. Arcanist is not core content.
    • Performance: three caches the review suggested were measured and not built (each under a millisecond). Do not add them without a measurement that says otherwise.
    • The detail card treats the action bar's strip as the foot of the screen. Rail windows were left alone: users arrange those.
    • Encounter of the Week covers its corner buttons with a full-screen stage during a montage or negotiation, so History cannot be opened then. Lines written there are read afterwards.
